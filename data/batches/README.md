# Benchmark batches — split by IBM access plan budget

`data/IBM_VQE_Test_Benchmark.csv` (2,436 rows) split into sequential
tranches sized to each IBM access plan's QPU-time budget, generated by
[`examples/guides/split_benchmark_batches.py`](../../examples/guides/split_benchmark_batches.py).
Regenerate with:

```sh
python examples/guides/split_benchmark_batches.py
```

## Files

| File | Rows | Est. QPU time | Plan budget | Fits? |
|---|---|---|---|---|
| `batch1_open_plan.csv` | 6 | 9.10 min | 10 min (Open Plan, free) | Yes, 0.90 min headroom |
| `batch2_flex_plan.csv` | 262 | 399.17 min | 400 min (Flex Plan minimum purchase) | Yes, 0.83 min headroom |
| `batch3_premium_plan.csv` | 1,298 | 2,063.49 min | 5,200 min (Premium Plan annual minimum) | Yes, 3,136.51 min headroom |
| `batch0_unestimable_needs_mol_map_run.csv` | 870 | unknown | — | Not batchable yet (see below) |

**1,566 + 870 = 2,436** — every row from the master CSV is accounted for
in exactly one file.

## Methodology

**Each plan's budget is independent, not cumulative** — batch2's 400
minutes is a *fresh* Flex Plan purchase, not "400 minutes on top of
whatever Open already covered." This matches the real workflow: you
exhaust the free Open Plan quota first, then buy a separate Flex Plan (or
subscribe to Premium) for the next tranche of work, each with its own
budget.

**Rows are sorted ascending by real estimated per-row QPU time** before
being greedily filled into each budget in order — batch1 gets the
cheapest calculations available (a smoke test before spending real
money/quota), batch2 the next-cheapest tranche, batch3 the rest. This is
why `batch1_open_plan.csv` turns out to be dominated by the 2-qubit
`H2`/`sto-3g`/`mol_map`-encoded cases (both `pauli` and `qasm_gen_grouped`
variants — see below) rather than, say, one row per molecule — if you'd
rather the first batch prioritize *coverage* over strict
cost-minimization, that's a different, equally valid sort strategy — ask
and I'll regenerate with it.

**Per-row QPU-time estimates are real, not guessed** — same method as
[`backends/ibm_cost_estimator.py`](../../docs/integrations/ibm_cost_estimator.md):
real ALAP-scheduled transpilation against `FakeBrisbane` (no credentials
needed) plus IBM's own documented usage formula. Real transpile calls are
cached per (qubits, ansatz reps) pair — only 72 distinct pairs across all
1,566 estimable rows, so this runs in ~20s rather than re-transpiling
1,566 times.

**`Measurement_Method` (`pauli` vs `qasm_gen_grouped`) does not change
this estimate.** The resource estimator has no way to know how many
distinct circuits Cebule's real QASM_GEN grouping would produce for a
given Hamiltonian — that's an output of a real run, not derivable from
the inputs (see `data/README.md`'s QASM_GEN section). So every `pauli`/
`qasm_gen_grouped` pair of an otherwise-identical row gets an *identical*
cost estimate here, and both land in the same batch together — a known
simplification, not a claim that the two measurement methods really cost
the same on real hardware. `qasm_gen_grouped` is expected to cost less
(that's the whole point of the method), so real per-row costs would very
likely reshuffle rows between batches, especially near a budget boundary.

**Illustrative assumptions carried over unchanged** from
`examples/guides/estimate_ibm_cost.py` (see that script and
`data/README.md` for why these remain open questions, not confirmed
values):

- 4,096 shots per circuit
- 30 VQE iterations per case (i.e. 30 separate circuit submissions, each
  paying its own ~2s per-sub-job overhead — this dominates the total for
  small circuits, which is part of why the cheapest rows cluster together
  rather than spreading smoothly)
- `EfficientSU2` ansatz, reps = `TN_Layers_Circuit` for `tn_qc_opt`/
  `tn_qc_opt+mol_map` rows (the one TN-VQE knob that changes the real
  submitted circuit — `TN_Layers_Network` runs classically and has zero
  effect on this estimate, see `data/README.md`), else 1 rep

**Extra columns** (`Est_QPU_Time_S_At_30_Iter`, `Est_QPU_Time_Cumulative_S`)
are appended to each batch file beyond the master CSV's own columns, for
auditability — the cumulative column should never exceed that file's plan
budget (converted to seconds).

## `batch0_unestimable_needs_mol_map_run.csv`

870 rows — every row using `mol_map` or `tn_qc_opt+mol_map` on a
(molecule, basis) combination where Cebule's constraint-based encoding
qubit count isn't already known (only H2 × 4 bases and Li2/H2O × sto-3g
have a real `mol_map` qubit count today — see `data/README.md`), doubled
by the `Measurement_Method` dimension. Without a qubit count there's no
circuit to transpile and nothing to estimate, so these rows are **not**
guessed into a batch — they need a real Cebule `MOL_MAP` run first
(`schemas.mqsdk_cebule.MolMapInput`) to get a real `N_Qubit`, after which
re-running the split script will place them into whichever tranche they
actually fit.

## No overflow — but headroom varies a lot

All 1,566 estimable rows fit within Open + Flex + Premium's combined
budget (no `batch4_overflow.csv` was produced). Premium's tranche has by
far the most slack (2,063.49 of 5,200 minutes used, 1,298 rows) — it
absorbs everything left over after Open and Flex are packed tight,
including the largest single case (`Li2`/`cc-pVTZ`/`JW`, 120 qubits,
~107s at 30 iterations). If you scale up the assumptions (more shots,
more iterations, more bases) or the real `qasm_gen_grouped` circuit
counts turn out lower than assumed here, Premium's headroom is what would
absorb it — worth re-running this split after any assumption change to
confirm batch1/batch2 still fit their tighter budgets.
