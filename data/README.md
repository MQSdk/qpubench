# `IBM_VQE_Test_Benchmark.csv`

The **stage-1 screening matrix** for the VQE benchmark campaign: 336
self-contained rows (no implicit inheritance from the row above),
generated by
[`examples/guides/build_benchmark_matrix.py`](../examples/guides/build_benchmark_matrix.py).
Regenerate with:

```sh
PYTHONPATH=src python examples/guides/build_benchmark_matrix.py
```

`PYTHONPATH=src` (or a `pip install -e .`) is required — the script
imports `qpubench`, and its own `sys.path` line adds the repo root, not
`src/`.

To run it as a real campaign, [`batches/`](batches/) splits the matrix
into tranches sized to IBM's Open / Flex / Premium plan QPU-time budgets,
with real transpile-based per-row estimates; methodology in
[`batches/README.md`](batches/README.md).

## Two stages, because the sweep has a decision point in the middle

> **Superseded figures below, kept as history.** The 2,436-row matrix
> described in this paragraph has not existed since commit `2e13e4d`.
> Cite the 336 rows above as current state, not these.

An earlier revision crossed every dimension with every other: 3 molecules
x 7 basis sets x 2 mappers x 28 tensor-network sweep points x 2
measurement methods = 2,436 rows and ~2,463 minutes of estimated QPU
time, with no mechanism for *deciding* anything. Every basis set got the
full 28-point sweep whether or not it had earned one.

The sweep is now split where the real decision falls:

| Stage | Purpose | Broad in | Shallow in | Rows |
|---|---|---|---|---|
| **1, screening** | Which basis set, ansatz, mapper and measurement method are worth pursuing | all 7 bases, 4 ansatz families, both mappers, both measurement methods | one TN-VQE reference point, one small fixed active space per molecule | 336 |
| **2, deep sweep** | The full 28-point TN-VQE sweep | TN_Layers_Network x TN_Layers_Circuit x TN_Ansatz | only the (molecule, basis, ansatz) combinations stage 1 selected | generated on demand |

Stage 2 is deliberately **not** committed in advance. The basis sets it
runs on are an *output* of stage 1, not an input to it, so generate it
once stage-1 results exist:

```sh
PYTHONPATH=src python examples/guides/build_benchmark_matrix.py --stage 2 \
    --select H2=cc-pvdz --select Li2=6-31g --select H2O=def2-svp \
    --ansatz EfficientSU2
```

The script refuses to run stage 2 without an explicit `--select`, because
there is no defensible default before the screening results exist.

### What stage 2's 28 points are, explicitly

Stated here rather than left implied by the generator's defaults. Four
families fit in the same 28 points two used to occupy, because the family
comparison is a *method* question, not a chemistry-coverage question, and
so does not need the full grid on every family:

| Slice | Points |
|---|---|
| `givens` on the full grid: `network=0` x 4 circuits, plus `network∈{1,2,3}` x 4 circuits | 16 |
| family-comparison core: `rotation_1param` / `rotation_3param` / `number_preserving`, at `network∈{1,3}` x `circuit∈{1,2}` | 12 |
| **total** | **28** |

Crossing all four families with the full grid would give 52 points and
636 rows (+83%) instead. Pinning `givens` as the reference family rather
than `rotation_3param` is a deliberate break with continuity: the old
`full` rows used a non-entangling U(θ), so they are not a baseline worth
preserving. `rotation_3param` survives inside the core, which is where
the comparison against the task's own default belongs.

`number_preserving` is marked in `Notes` as a **control**, not a
candidate: it is expected to inflate measurement cost without an accuracy
gain, and it is the first arm to cut if budget tightens.

`--sweep-circuit-ansatz` additionally crosses the 12-point core with
`excitation_preserving_linear` (see `Ansatz` below). It is **off by
default** because it takes the sweep from 28 to 40 points and the file
from 348 to 492 rows, and because `xx_plus_yy` is not a FakeBrisbane
basis gate — re-cost before enabling it rather than assuming parity.

## The active space is held fixed across basis sets

Every stage-1 row for a given molecule uses the same active space,
regardless of basis. That is what makes stage 1 a basis-set screen rather
than a confound: the basis is the only thing varying, so a stage-1 energy
difference is attributable to it.

| Molecule | Electrons | Active space | Frozen | JW qubits | mol_map qubits |
|---|---|---|---|---|---|
| `H2` | 2 | CAS(2,2) | nothing to freeze | 4 | 2 |
| `Li2` | 6 | CAS(2,2) | both Li 1s orbitals | 4 | 2 |
| `H2O` | 10 | CAS(8,6) | O 1s | 12 | 8 |

This is also what makes the campaign runnable at all: qubit counts no
longer scale with the basis set, so `H2O`/cc-pVTZ costs the same 12 JW
qubits as `H2O`/sto-3g instead of 116. Stage 2 can opt back into the full
space with `--active-space full` where the hardware (or the local machine
running MOL_MAP) can take it.

## Mapper and method are separate columns

`Mapper` records only the fermion-to-qubit mapping, which is what the
word means. Cebule's TN_QC_OPT is not a mapping and not an ansatz; it is
the optimisation method wrapped around one, so it lives in `Method`:

| Column | Values | Meaning |
|---|---|---|
| `Mapper` | `JW` | Jordan-Wigner, `2 x active_orbitals` qubits |
| | `mol_map` | Cebule's constraint-based encoding, fewer than `2N` qubits |
| `Method` | `VQE` | plain variational eigensolver |
| | `TN-VQE` | Cebule TN_QC_OPT, tensor network plus circuit |
| `Ansatz` | `EfficientSU2`, `RealAmplitudes`, `UCCSD`, `n_local_rzryrz_sca` | the actual circuit family |

`UCCSD` appears on `JW` rows only: it builds excitation operators from
fermionic modes, which needs a fermion-to-qubit mapping to sit on, and
mol_map's qubits index determinants rather than spin orbitals.

`n_local_rzryrz_sca` is TN_QC_OPT's **Qiskit** circuit side —
`n_local(n, ["rz","ry","rz"], "cx", entanglement="sca")` — which is what
runs in an IBM campaign. The task's PennyLane path builds a different
circuit, `StronglyEntanglingLayers`, with a different parameter count
(`3nR` against `3n(R+1)`). Earlier revisions of this matrix named the
PennyLane circuit on rows destined for IBM hardware, which understated
`Num_Opt_Params_Phi` by 50% on every TN row. `Backend_Platform` now pins
which one a row means.

## The four TN rotation families

`TN_Ansatz` replaces the old `Rotation_Type` column, whose `full` /
`phase` values named only two of the four families the method really has
(`M_ANSATZE`, `functions_U.py:150-161`). The old names are not kept as
aliases: they are ambiguous now that `givens` is also a rotation and
`number_preserving` is also "full".

| `TN_Ansatz` | params/node | entangles | conserves N |
|---|---|---|---|
| `rotation_1param` | 1 | no | no |
| `rotation_3param` | 3 | no | no (the task's own default) |
| `givens` | 1 | **yes** | **yes** |
| `number_preserving` | 5 | **yes** | **yes** |

Both `rotation_*` families are **non-entangling**: the network factorises
across the two wires of every M gate, so U(θ) cannot entangle at all — it
only rotates each qubit's local basis. A matrix sweeping just those two
sweeps two variants of "no entanglement in U(θ)" and never touches the
case the method exists for.

**Stage 1's single TN reference point uses `givens`.** It entangles,
conserves particle number, and is the only family with a fast path in the
implementation (`_orbital_pauli_terms` routes it through
`OrbitalRotationHamiltonian` at O(N⁵) instead of contracting the network
at 2ⁿ cost), so it is also the family whose stage-1 timings resemble
stage 2's. The switch cost nothing: the family changes U(θ), not the
circuit, so every per-row QPU estimate is unaffected. If you would rather
screen on the task's own default for continuity, change
`STAGE1_TN_REFERENCE` in the generator — it is one constant.

## Columns

| Column | Meaning |
|---|---|
| `Case_ID` | Row index |
| `Stage` | `1_screen` or `2_deep` |
| `Molecule`, `Charge`, `Multiplicity`, `Num_Electrons` | `H2`, `Li2`, `H2O`, all neutral closed-shell singlets |
| `Basis`, `Basis_Source` | 6 [Basis Set Exchange](https://www.basissetexchange.org/) names or `qvSZP`; see [docs/integrations/basis_sets.md](../docs/integrations/basis_sets.md) |
| `Active_Space` | `valence_cas` (core frozen) or `full` |
| `Active_Electrons`, `Active_Orbitals` | The space the Hamiltonian is built in; maps onto `BenchmarkRecord.active_electrons` / `.active_orbitals` |
| `Mapper`, `Method`, `Ansatz` | See table above |
| `Ansatz_Reps` | Circuit repetitions; equals `TN_Layers_Circuit` on TN-VQE rows |
| `N_Qubit`, `N_Qubit_Source` | Qubit count and where it came from: `jw_exact`, `mol_map_run` (a real MOL_MAP run) or `mol_map_inferred` (see below) |
| `Backend_Platform` | Which platform's circuit the row means: `qiskit.aer` (`TNQCOptInput.backend`) on TN rows, `ibm_runtime` (qpubench's own `IBMAdapter`) on VQE rows. Without it, `Num_Opt_Params_Phi` is ambiguous |
| `Optimizer`, `Opt_Options` | `COBYLA`, matching `TNQCOptInput.opt_method`'s default, and the `opt_options` dict passed straight to `scipy.optimize.minimize`. `{}` is a *recorded* choice, not an unexamined one — for COBYLA, `rhobeg` changes both convergence and the evaluation count, i.e. the row's QPU cost |
| `Shots` | 4,096, pinned via `TNQCOptInput.n_shots`; `0` on rows that run no circuit |
| `Qiskit_Version` | The installed Qiskit, recorded because `transpile`'s default `optimization_level=None` resolves to 2 under Qiskit 2.x and 1 under 1.x — "Qiskit's default" is not a fixed value |
| `TN_Layers_Network`, `TN_Layers_Circuit` | TN-VQE sweep: θ (classical TN side, 0 to 3; 0 = "circuit only" baseline) and φ (quantum circuit side, 1 to 4). Ranges match the reference paper ([arXiv:2402.12105](https://arxiv.org/abs/2402.12105)) |
| `TN_Ansatz` | One of the four families above, or `n/a (no TN layers)` / `n/a (not TN-VQE)` |
| `Optimization_Mode` | `both` (jointly optimise θ and φ) or `network` (θ only, no quantum measurements — the zero-QPU control, see below) |
| `Measurement_Method` | `pauli` or `grouped`, matching `TNQCOptInput.measurement_method` exactly |
| `Qasm_Ansatz_File`, `Qasm_Ansatz_SHA256` | The pinned circuit under `data/qasm/` and a hash prefix of it, so a silently edited circuit stops matching. Generated by [`pin_qasm_ansatz.py`](../examples/guides/pin_qasm_ansatz.py); blank when no file has been pinned |
| `Num_Opt_Params_Phi` | Circuit-side parameter count, computed per `Backend_Platform`; blank for `UCCSD`, whose count depends on the generated excitation list |
| `Num_Opt_Params_Theta` | Network-side parameter count. Derivable from the inputs, unlike the column below: `TN_Layers_Network x ((3n - 2) // 2) x params_per_node` |
| `Num_ExpVals_Per_Iter` | Blank — an output of a real run, not derivable from inputs |
| `Notes` | Per-row provenance and caveats |

### `Num_Opt_Params_Theta` is not just bookkeeping

With COBYLA the iteration count scales with the parameter count, so a
`number_preserving` row is **5x** the classical optimisation work of a
`givens` row at the same layer count. At stage 1's
`TN_Layers_Network = 2` that is 4 / 12 / 20 parameters at 2 qubits, up to
34 / 102 / 170 at 12.

`Num_ExpVals_Per_Iter` stays blank because it genuinely is a run output —
and it is the measurement that would support this campaign's most
defensible headline: *`givens` + `grouped` keeps measurement cost flat as
`TN_Layers_Network` grows, `number_preserving` does not.*

### The zero-QPU classical-only control

42 rows (one per molecule x basis x mapper) run
`optimization_mode="network"`: θ is optimised by classical tensor-network
contraction and φ is frozen, so **no quantum measurements are taken at
all**. They cost nothing against any IBM plan budget and live in
`batches/batch0_classical_only.csv`, outside the plan tranches.

They exist because they are the floor every `both` row must be measured
against. This matters most on exactly the `givens` rows stage 1 now
screens with: there U(θ) is an orbital rotation and can carry a large
part of the correlation energy by itself, so without the control a `both`
run reads as a quantum success when most of the result came from the
classical half.

### `Measurement_Method` uses Cebule's own vocabulary

The two values are `pauli` and `grouped`, exactly as
`schemas.mirrors.mqsdk_cebule.TNQCOptInput.measurement_method` defines
them. An earlier revision called the second one `qasm_gen_grouped`, which
was a misnomer on TN_QC_OPT rows: TN_QC_OPT uses the same
basis-state-pair-grouping *idea* as the standalone QASM_GEN task, but
generates no QASM files, so naming the task in the value implied a
pipeline step that does not run.

`tests/test_docs_consistency.py` now checks this column, and `TN_Ansatz`,
against the mirror's own vocabulary — the drift that produced
`qasm_gen_grouped` and `full`/`phase` is exactly what that test is for.

### Why there is no `Qiskit_Opt_Level` column

TN-VQE calls `transpile(circuit, backend)` with no `optimization_level`
argument and offers no way to pass one (`functions_qiskit.py:47,205`), so
the column could never be set from a task input. It is dropped rather
than left blank. `Qiskit_Version` records the thing that actually
determines the level, since `transpile`'s own default is version-
dependent.

## mol_map qubit counts are now computed, not left blank

Cebule's MOL_MAP encoding indexes only the determinants that satisfy the
particle-number and spin constraints, so its qubit count follows the
active space rather than the basis-set size:

```
n_qubits = ceil(log2( C(n_orbitals, n_alpha) x C(n_orbitals, n_beta) ))
```

This is **inferred**, not documented by Cebule, but it reproduces all
eight real MOL_MAP counts this project knows about exactly, including
both values that arrive independently of the fit
([`hamiltonian_sources/mol_map.py`](../src/qpubench/hamiltonian_sources/mol_map.py),
pinned by `tests/test_mol_map.py`):

| Molecule / basis | (orbitals, alpha, beta) | Determinants | Qubits |
|---|---|---|---|
| H2 / sto-3g | (2, 1, 1) | 4 | 2 |
| H2 / 6-31G | (4, 1, 1) | 16 | 4 |
| H2 / cc-pVDZ | (10, 1, 1) | 100 | 7 |
| H2 / def2-SVP | (10, 1, 1) | 100 | 7 |
| H2 / def2-TZVP | (12, 1, 1) | 144 | 8 |
| H2 / cc-pVTZ | (28, 1, 1) | 784 | 10 |
| H2O / sto-3g | (7, 5, 5) | 441 | 9 |
| Li2 / sto-3g | (10, 3, 3) | 14,400 | 14 |

Two checks that this is the rule and not a coincidental fit: H2/cc-pVDZ
and H2/def2-SVP are different basis sets with the same active space and
the same reported count, which no basis-size formula predicts; and
Li2/sto-3g and H2/cc-pVDZ share 10 orbitals but differ in electron count,
giving the 14 and 7 the formula requires.

Consequence: the 870-row `batch0_unestimable_needs_mol_map_run.csv` that
previous revisions could not cost at all is gone. Every row now has a
qubit count. Rows whose count comes from the formula rather than a real
run are marked `mol_map_inferred` in `N_Qubit_Source`, so they stay
distinguishable from measured ones; treat them as good enough to size a
circuit and cost a batch, not as a substitute for a real MOL_MAP run.

## Known limitations

- **Cost estimates treat `pauli` and `grouped` rows as identical.** The
  circuit-count reduction is an output of a real run, so the
  [IBM cost estimator](../docs/integrations/ibm_cost_estimator.md) and
  `batches/` cannot account for it. `grouped` is expected to cost less,
  so real per-row costs would reshuffle rows between batches.
- **`TN_Layers_Network` is classical compute, not QPU time.** Only
  `TN_Layers_Circuit` affects IBM billing; the two costs move
  independently.
- **qvSZP qubit counts are computed offline** via
  `hamiltonian_sources.qvszp` (a `34 -> 36` Li2 error in an earlier draft
  was caught this way).
- **Geometries are unspecified.** Every row names a molecule and a basis
  but no bond length, still an open campaign decision.
- **`phi_init`'s real shape is unverified.** The Cebule mirror types it
  `list[float]`, which is probably wrong for the PennyLane path's
  `(L, N, 3)` circuit — but that is an inference, and it is flagged
  rather than asserted pending a check against a real job response.

checked 2026-07-09) and [arXiv:2402.12105](https://arxiv.org/abs/2402.12105),

## Open campaign decisions

Unresolved choices are tracked as a git-bug item; run
`git bug bug --status open` and look for "IBM VQE campaign". Shots,
transpiler optimisation level, `n_iterations`, scale and
`optimization_mode` are now settled and recorded above; geometries and
whether to run the full space on the larger bases are still open.
