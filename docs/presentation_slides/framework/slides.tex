\begin{frame}[fragile]{What is QPUBench?}

\midrule\noalign{}
\endhead
\textbf{Schema} & \emph{What} are you benchmarking? & \texttt{schemas/}:
37 Pydantic v2 modules (= ``Schema v5.0.0'') \\
\textbf{Adapter} & \emph{How} does it run? & \texttt{backends/} +
\texttt{integrations/} (next slide) \\
\textbf{Store} & \emph{How} is it persisted? & \texttt{store.py}:

\bottomrule\noalign{}
\end{longtable}

\normalsize

\begin{block}{Core invariants}
\texttt{qpubench} itself never imports from any quantum library; only adapters do. And since schema v3.0.0 the core schema modules import \emph{zero vendor schema modules}: vendor data flows through vendor-neutral dict extension points (next section).
\end{block}
\end{frame}

\begin{frame}[fragile]{Architecture}
\phantomsection\label{architecture}
\footnotesize

\begin{columns}[T]
\begin{column}{0.5\textwidth}
\textbf{Core layer} \emph{(no SDK deps, \texttt{pip\ install}-able)}

\begin{itemize}
\tightlist
\item
  \texttt{schemas/}: Schema layer
\item
  \texttt{runner.py}: \texttt{BenchmarkRunner}
\item
  \texttt{store.py}: Store layer
\end{itemize}
\end{column}

\begin{column}{0.5\textwidth}
\textbf{Integration layer} \emph{(reference code)}

\begin{itemize}
\tightlist
\item
  \texttt{backends/}: adapter protocols + stubs
\item
  \texttt{integrations/}: real reference adapters, \textbf{not
  installed}; copy into your project (like a template)
\item
  \texttt{examples/}: runnable demos
\end{itemize}
\end{column}
\end{columns}

\normalsize

\begin{verbatim}
┌─────────────────────┐     ┌─────────┐     ┌─────────────────┐     ┌───────┐
│ CircuitSpec/Problem │ ──▶ │ Adapter │ ──▶ │ BenchmarkRecord │ ──▶ │ Store │
└─────────────────────┘     └─────────┘     └─────────────────┘     └───────┘
\end{verbatim}

\footnotesize

\textbf{``Contract''} = a Python \texttt{Protocol}, a fixed method
signature (\texttt{spec}/\texttt{validate}/\texttt{run}) callers rely on
without caring which class implements it. A \textbf{stub} satisfies it
with fake data; real adapters (Aer, IBM, IQM, Braket) satisfy the same
contract with real SDK calls. Swapping one for the other needs zero code
changes elsewhere. \normalsize
\end{frame}

\begin{frame}[fragile]{Key Design Principles}
\phantomsection\label{key-design-principles}
\footnotesize

\begin{longtable}[]{@{}
  >{\raggedright\arraybackslash}p{(\columnwidth - 2\tabcolsep) * \real{0.4231}}
  >{\raggedright\arraybackslash}p{(\columnwidth - 2\tabcolsep) * \real{0.5769}}@{}}
\toprule\noalign{}
\begin{minipage}[b]{\linewidth}\raggedright
Principle
\end{minipage} & \begin{minipage}[b]{\linewidth}\raggedright
Implementation
\end{minipage} \\
\midrule\noalign{}
\endhead
\textbf{Schema-first} & Pydantic v2 models are the stable contract;
every record round-trips through \texttt{.model\_dump\_json()} \\
\textbf{No SDK lock-in} & Core never imports any quantum library \\
\textbf{Three adapter protocols} & \texttt{BackendAdapter} ·
\texttt{AlgorithmAdapter} · \texttt{ErrorMitigationAdapter} \\
\textbf{Append-only stores} & \texttt{NDJSONStore}/\texttt{ParquetStore}
for reproducible sweeps; \texttt{S3Store} for concurrent writers \\
\textbf{Language-agnostic} & Every record is plain JSON, so any language
can parse it, whichever store wrote it \\
\textbf{Inputs vs.~outputs} & \texttt{VQAConfig} = what you chose to
run; \texttt{VQAResult} = what the run produced; computed values are
never user-supplied \\
\textbf{Vendor-neutral core} & Vendor payloads live in keyed dicts
(\texttt{vendor\_results}, \texttt{mitigation\_options},
\texttt{vendor\_data}); adding a vendor never touches a core file \\
\bottomrule\noalign{}
\end{longtable}

\normalsize
\end{frame}

\begin{frame}[fragile]{NDJSON vs.~JSON, Precisely}
\phantomsection\label{ndjson-vs.-json-precisely}
\footnotesize

Every \texttt{BenchmarkRecord} serializes to one JSON object, always.
\emph{How that object reaches disk} differs by store: same schema, three
storage strategies, not an inconsistency:

\begin{longtable}[]{@{}
  >{\raggedright\arraybackslash}p{(\columnwidth - 2\tabcolsep) * \real{0.5000}}
  >{\raggedright\arraybackslash}p{(\columnwidth - 2\tabcolsep) * \real{0.5000}}@{}}
\toprule\noalign{}
\begin{minipage}[b]{\linewidth}\raggedright
Store
\end{minipage} & \begin{minipage}[b]{\linewidth}\raggedright
On-disk shape
\end{minipage} \\
\midrule\noalign{}
\endhead
\texttt{NDJSONStore} & One JSON object per line, appended to one shared
file (``\textbf{N}ewline-\textbf{D}elimited JSON'') \\
\texttt{S3Store} & One whole JSON file per record; no shared file, so
concurrent writers can't race \\
\texttt{ParquetStore} & Same records converted to a columnar table \\
\bottomrule\noalign{}
\end{longtable}

\normalsize
\end{frame}

\begin{frame}[fragile]{Reading This Reference}
\phantomsection\label{reading-this-reference}
\footnotesize

The next 9 slides are a \textbf{reference listing}, not a narrative;
they exist so you know a module is there when you need it, not to be
read top-to-bottom. The take-home message fits in one line: \normalsize

\begin{block}{Take-home message}
Every schema module is a set of typed Pydantic models for one vendor/technique's inputs and outputs. 11 "core" modules are framework-owned (no vendor); the rest are one module per integration, named so the filename alone tells you who maintains it.
\end{block}

\vspace{0.3em}
\footnotesize

\textbf{If you just want to see the package in action}: skip ahead to
\emph{Adapters} (real running code) or \emph{Examples \& Coverage} at
the end (a full worked example). Come back here when you need to look up
what a specific module contains; that's what a GitHub repo's own
reference docs (\texttt{docs/schemas.md}) are for; these slides just
mirror the module list so it's not a total blank spot. \normalsize
\end{frame}

\begin{frame}[fragile]{The three module groups}
\phantomsection\label{the-three-module-groups}
The schema library splits into \textbf{three groups} (same split as
\texttt{docs/schemas.md}):

\begin{enumerate}
\tightlist
\item
  \textbf{Core record format}: the unprefixed modules defining the types
  every benchmark shares: \texttt{primitives} · \texttt{circuit} ·
  \texttt{observable} · \texttt{backend} · \texttt{execution} ·
  \texttt{result} · \texttt{record}.
\item
  \textbf{Cross-cutting catalogues \& registries}
  (\texttt{schemas/catalogs/}): modules that aggregate \emph{multiple}
  external sources or define framework-own catalogues:
  \texttt{quantum\_advantage\_tracker} · \texttt{optimizer\_catalog} ·
  \texttt{hamiltonian\_library} · \texttt{basis\_sets} ·
  \texttt{contraction\_path} · \texttt{reactions} ·
  \texttt{polarizable\_embedding} · \texttt{fragmentation} ·
  \texttt{distributed\_execution}.
\item
  \textbf{Project mirrors} (\texttt{schemas/mirrors/}): one module per
  external project, named
  \texttt{\textless{}org\_or\_maintainer\textgreater{}\_\textless{}package\textgreater{}.py}
  so the filename alone names the upstream source.
\end{enumerate}

\vspace{0.3em}

Two orthogonal axes, \textbf{computing model} (paradigm) and
\textbf{qubit modality} (QPU), are stamped on every circuit, backend,
and result, independently of the group.
\end{frame}

\begin{frame}[fragile]{What Is Kubeflow, and Why Is It Here?}
\phantomsection\label{what-is-kubeflow-and-why-is-it-here}
\footnotesize

\textbf{For readers who haven't met Kubeflow}: an open-source platform
that runs a workflow as a graph of steps (a DAG) on Kubernetes: each
step is a container; it schedules them, tracks inputs/outputs, and shows
the graph in a web dashboard.

\begin{verbatim}
mol_map ──▶ tn_qc_opt ──▶ qasm_gen ──▶ execute_circuits
  (box)        (box)         (box)          (box)
\end{verbatim}

\textbf{Why it's here}: earlier integrations only needed
\texttt{runner.run()}. Kubeflow becomes useful once a \emph{sequence} of
qpubench steps needs to run unattended, on a schedule, with a visual
record, e.g.~a nightly benchmark sweep. The next slides show that
sequence as a real, compiled Kubeflow pipeline. \normalsize
\end{frame}

\begin{frame}{Methodology: Honest by Construction (1/2)}
\phantomsection\label{methodology-honest-by-construction-12}
\footnotesize
\begin{block}{No fabricated chemistry}
Illustrative qubit Hamiltonians (\texttt{toy\_hamiltonians.py}) stay explicitly labeled, never presented as physically accurate. Real molecules: \texttt{qforte\_vqe\_benchmark.py} (He/cc-pVDZ) and \texttt{hamiltonian\_sources/}, where real ab initio Hamiltonians replaced toy ones in 3 tutorials, checked against real reference notebooks.
